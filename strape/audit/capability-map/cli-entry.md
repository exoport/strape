## What this area can do (prose)

This is the process bootstrap: it parses argv (`cli/args.ts`), decides interactive vs. print vs. rpc mode, runs one-time on-disk migrations of legacy credential/session files, resolves which project directory's local config is safe to honor (project-trust), stands up a pre-trust TUI for first-run setup/session-resume/missing-cwd prompts, and then hands off to `modes/index.ts` (out of scope) to actually run the agent. It also implements the entire `pi install/remove/update/list/config` package-manager surface, including a self-update path that shells out to `npm`/`pnpm`/`yarn`/`bun` with `--ignore-scripts` but also with `--min-release-age=0`/`--minimum-release-age=0` (explicitly defeating registries' "wait before installing a brand-new version" anti-supply-chain-attack feature). It owns the one CLI surface that exists purely to leak secrets on purpose — `pi auth print-api-key`/`print-bearer-token` prints a live, usable provider credential to stdout with no extra confirmation — and it computes the on-disk location of every session transcript, a computation that (see Questions below) reads project-local `.pi/settings.json` before project trust has been decided at all. Nothing here executes model-supplied tool calls directly (that's `core/`); this area's job is to get from `argv` to a `CreateAgentSessionOptions` safely.

## Dismissed sweep hits (with reason)

- **`process-exec` × 4** (`credential-print.ts:54,129`; `config.ts:128,230`) — all four are `RegExp.prototype.exec()` calls (`/^Bearer\s+(.+)$/iu.exec(...)`, `/^(\d+)(ms|s|m|h)$/iu.exec(...)`, `/^(.*[\\/]global[\\/][^\\/]+)[\\/]\.pnpm[\\/]/.exec(...)`). The regex sweep matches the literal substring `exec(` and cannot distinguish `RegExp#exec` from `child_process.exec`. No process spawning occurs at any of these lines.
- **`trust` — most of `package-manager-cli.ts` and `args.ts`** (e.g. `args.ts:274,276,292,293`; `package-manager-cli.ts:82-183`) — these are `--help` usage strings describing `--approve`/`--tools`/`--exclude-tools`; they are documentation, not enforcement. The real enforcement is the small set of call sites listed in the trust table above.
- **`trust` — `index.ts:330`, `main.ts:24,41,52`, `package-manager-cli.ts:5,22,25`** — plain `import { ... } from "./core/trust-manager.ts"` / `"./core/project-trust.ts"` statements or type re-exports. They establish that trust logic is *used* here (which is why the real call sites are analyzed above) but the import line itself has no behavior.
- **`network` — `args.ts:407`, `config.ts:336`, `migrations.ts:12,14`, `package-manager-cli.ts:126`** — literal URL strings inside `--help` text or a migration-guide pointer printed to the console; no request is issued from these lines.
- **`credentials` — `credential-print.ts:29,116,131,134,135,149`; `migrations.ts:23,24`** — variable/array declarations, doc-comment prose, and `join(agentDir, "auth.json")` path-string construction. Real capability is in the functions these lines sit inside, already covered in the credentials table.
- **`deserialize` — none dismissed**; all 5 in-scope hits are genuine `JSON.parse` call sites (see table above).
- **`env`, `fs-write` — none dismissed**; every in-scope hit corresponds to a real `process.env`/`fs` operation.

## Capabilities found by reading, missed by the sweep

1. **Real `process-exec` capability entirely missed** (self-update `spawnProcess` calls in `package-manager-cli.ts` and package-root detection `spawnProcessSync` calls in `config.ts`) — see process-exec table. The sweep's zero-true-positive count for this class in this scope is itself a finding: it demonstrates the regex sweep cannot follow the `spawnProcess`/`spawnProcessSync` wrapper indirection in `utils/child-process.ts`.
2. **Dynamic-code entry points, not dynamic-code execution itself**: `args.ts` parses `-e/--extension`, `--skill`, `--prompt-template`, `--theme` (each taking an arbitrary filesystem path) into `parsed.extensions/skills/promptTemplates/themes`, which `main.ts:670-673,723-736` resolves to absolute paths and forwards as `additionalExtensionPaths` etc. into `createAgentSessionServices` (`core/`, out of scope, where the actual `import()`/execution happens). No `eval`/`import()`/`require()` appears anywhere in this scope's files (verified by direct grep), so the sweep correctly found zero `dynamic-code` hits here — but the *trigger surface* for that capability elsewhere is rooted in these CLI flags and is worth the human reviewer cross-referencing against whatever gates extension loading in `core/extensions/`.
3. **Project-trust bypass for session storage location** (not a sweep class at all, found purely by tracing control flow): `main.ts:617` constructs `startupSettingsManager = SettingsManager.create(cwd, agentDir)` **without** `{projectTrusted:false}`. `SettingsManager.fromStorage` (`core/settings-manager.ts:325`) defaults the omitted option to `true`, so it unconditionally parses and merges `<cwd>/.pi/settings.json` — a file that itself is on the `TRUST_REQUIRING_PROJECT_CONFIG_RESOURCES` list (`core/trust-manager.ts:29-37`) precisely because it's supposed to require a trust decision first. `main.ts:632-637` then calls `startupSettingsManager.getSessionDir()` (which reads the deep-merged, project-influenced `this.settings`, confirmed at `core/settings-manager.ts:675-677`) to pick the directory where the **real** session transcript for the run gets created, before `resolveProjectTrusted` ever runs (`main.ts:661` onward) and independent of `--no-approve`. See "Questions for the human reviewer" — this is the single highest-value finding from this section. I confirmed by reading, not by dynamic execution.
4. **`pi auth print-*` as a credential-exfiltration primitive via the `bash` tool** — not a new code path, but its significance as an attack primitive is easy to miss by reading `cli/credential-print.ts` in isolation: it is a fully-formed, zero-extra-confirmation "print my live API key/OAuth bearer token to stdout" command that ships in the same binary the agent's own `bash` tool would invoke. Documented in the credentials table above.
5. **`experimental/` client/server scaffold is unreachable dead code** — `experimentalCli` (`cli/experimental/cli.ts:7`) composes `pi`/`server`/`client` sub-command parsers with unix-socket-only transports (`transport-address.ts` explicitly rejects any non-`unix://` scheme and validates the path is absolute with no traversal/embedded-NUL tricks — this part is well-hardened). But `grep -rn "experimentalCli|runServer|runClient"` across `src/` outside `cli/experimental/` returns nothing: it is only imported from `test/experimental-cli-*.test.ts`. `runServer`/`runClient`/`runPi` are unimplemented interface methods with no concrete class anywhere in this scope. **This surface currently cannot be reached from any shipped binary** (`cli.ts`, `rpc-entry.ts`) — flagged so the human reviewer doesn't mistake test-only scaffolding for a live network listener, and so it gets re-checked if it's ever wired up later.
6. **`--min-release-age=0` / `--minimum-release-age=0` in self-update** — not a sweep-classed pattern, but worth surfacing next to the process-exec finding: `package-manager-cli.ts`'s self-update path (via `config.ts:getSelfUpdateCommandForMethod`) explicitly opts out of npm/pnpm/bun's "don't install a version published in the last N days" supply-chain protection for its own upgrades.

## Questions for the human reviewer

1. **Is the `startupSettingsManager` / `sessionDir` project-trust bypass (`main.ts:617,632-637`) intentional or a bug?** Concretely: can a cloned, never-trusted repository's `.pi/settings.json` `{"sessionDir": "<attacker path>"}` redirect the *entire* session transcript (which can include file contents, command output, and anything the user pastes) to an attacker-chosen directory — e.g., a path inside the repo itself, so the transcript later gets `git add -A && git commit && git push`-ed by the unsuspecting user — before the project-trust prompt ever fires, and even if the user later answers "don't trust" or passes `--no-approve`? I traced this via static reading only (`SettingsManager.fromStorage` default `projectTrusted:true` at `core/settings-manager.ts:325`, confirmed `getSessionDir()` reads the merged/project-influenced `this.settings` at `core/settings-manager.ts:675-677`, confirmed `getDefaultProjectTrust()` is *not* similarly affected because it explicitly reads `this.globalSettings` at `core/settings-manager.ts:904-906`). This deserves a dynamic repro (clone a throwaway repo with a crafted `.pi/settings.json`, run `pi -p "hi" --no-approve`, and check where the `.jsonl` session file actually lands) before being treated as confirmed, but the code path is unambiguous on paper. If confirmed, this looks like a sibling of CVE-2026-54325's threat class ("acting on untrusted project content without approval") even though it's a settings field, not extension code execution.
2. **Does `pi install <source>` (non-`-l`, global scope) execute any code at install time** (npm lifecycle scripts, git hooks, postinstall) before the human ever runs `pi` again to load the new extension? The invocation lives in `package-manager-cli.ts:768-771` (`packageManager.installAndPersist`), but the mechanics are entirely in `core/package-manager.ts`, out of this section's scope. The strape commit `fac9677ee` mentions "empty install-script allowlist" as a hardening — worth confirming with whoever reviews `core/package-manager.ts` that this applies to `pi install` of arbitrary `npm:`/`git:`/`https://` sources typed by the user (or by a compromised agent via the `bash` tool), not just to the monorepo's own build.
3. **Is there any rate-limit/confirmation on `pi auth print-bearer-token`** given it actively refreshes and persists OAuth credentials as a side effect of merely being asked to print them (`cli/credential-print.ts:81-83` comment: "this intentionally calls `ModelRuntime.getAuth()`... refreshes and persists")? If the `bash` tool is ever auto-approved (allow-listed) for `pi`/the app binary itself in any configuration, this becomes a one-line credential exfiltration primitive with no additional gate in this section's code.
4. **Leftover `oauth.json.migrated`** (`migrations.ts:41`) — should this legacy migration also `chmodSync(0o600)` the renamed file, or delete it after successful migration, instead of leaving old plaintext OAuth tokens on disk indefinitely at their original (possibly loose) permissions?
5. Confirm with whoever owns `utils/windows-self-update.ts` that the Windows self-update quarantine path (`main.ts:537-539`, `package-manager-cli.ts:528-536`) — called unconditionally on every Windows startup — is the fix location for CVE-2026-54328 (predictable temp paths). From a quick read it scopes its quarantine directory under `node_modules/.pi-native-quarantine/<timestamp>-<pid>-<randomUUID>`, which looks appropriately unpredictable and not under a world-writable shared temp dir, but this file is out of this section's scope for a full review.
