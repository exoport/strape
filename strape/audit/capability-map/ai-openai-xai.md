## What this area can do (prose)

This area is the harness's only sanctioned way to talk to a real LLM: it turns an internal `Context` (system prompt + message history + tool schemas, all of which can contain attacker-injected text per T1) into HTTP(S) requests against `api.openai.com`, `api.x.ai`, `chatgpt.com/backend-api` (Codex), `auth.openai.com` and `auth.x.ai` (OAuth), and streams the model's response (including tool calls the model wants to invoke) back into the agent loop. Every model turn — automatic or user-initiated — flows through one of `openai-completions.ts`, `openai-responses.ts` or `openai-codex-responses.ts`; the latter additionally opens raw `wss://` WebSocket connections to the ChatGPT backend and shells zstd-compresses request bodies via `node:zlib`'s builtin module accessor. Credential handling is confined to attaching a `Bearer` token / `Authorization` header built from either a static API key (env var or user-entered secret) or an OAuth access token (acquired via a PKCE browser flow with a loopback HTTP server for OpenAI, or a device-code flow for xAI); no code in this area writes those credentials to disk (persistence is `auth/credential-store.ts`, out of scope) or executes anything beyond parsing JSON/SSE/WebSocket frames from the wire. There is no `process-exec`, `fs-write`, `temp-paths`, or trust/approval logic anywhere in these 17 files — the sweep's zero hits for those classes in this scope are accurate, not false negatives.

## Dismissed sweep hits (with reason)

- **`dynamic-code` — all `import("./openai-*.ts")` and `import("node:crypto"/"node:http")` hits** (openai-completions.lazy.ts:4, openai-responses.lazy.ts:4, openai-codex-responses.lazy.ts:4, auth/oauth/openai-codex.ts:12,15): every specifier is a **static string literal** known at build time. This is the harness's standard lazy-provider-load pattern (see `packages/ai/test/lazy-module-load.test.ts` referenced in `strape/docs/HUNKS.md`), not a path computed from user/model/repo input. No indirection was found that lets an attacker choose what gets imported.
- **`network` — `const AUTH_BASE_URL = "https://auth.openai.com"` and sibling URL constants** (auth/oauth/openai-codex.ts:27,30,39; auth/oauth/xai.ts:10-11): these are hardcoded string literals matched by the sweep's `https?:\/\/` regex, not runtime network calls themselves — the actual `fetch`/`WebSocket` call sites are reported separately above.
- **`network` — `let _http: typeof import("node:http") | null = null;`** (auth/oauth/openai-codex.ts:10, also double-counted as `dynamic-code`): a type-only/module-reference declaration, not a network operation.
- **`network` — `throw new Error("WebSocket transport is not available in this runtime")` and other `WebSocket`-mentioning error-message/class-definition lines** (openai-codex-responses.ts:962,984,1046,1106,1230,1243,1249,1303,1358,1377): matched because the string `WebSocket` appears in an error message, a type name, or a `class X extends WebSocket` declaration — not each one a distinct network egress point. The real WebSocket connection sites are `connectWebSocket` (line ~1057, `new WebSocketCtor(...)`) and `processWebSocketStream` (`socket.send`, line 1504), both covered in the inventory.
- **`credentials` — function/parameter names like `getClientApiKey`, `apiKey: string,`, `refreshAccessToken(refreshToken: ...)`** (openai-completions.ts:72,639; openai-responses.ts:43,216; openai-codex-responses.ts:271-294,511-516; auth/oauth files throughout): most of the 45 `credentials` hits are identifier names (parameters, function signatures) rather than distinct capability sites — one entry per identifier occurrence, not one leak per line. Consolidated into the inventory rows above by function, not by line.
- **`credentials` — `credentials/i` regex matches on the word "credential(s)" in type names / comments** (e.g. `OAuthCredential`, `credentialsFromToken`, `credentialsFromTokenResponse`): naming, not a new capability beyond what's already listed under the OAuth flow rows.
- **`env` — `provider-env.ts:16` `process.versions?.bun` check**: this is a runtime-detection guard, not itself an env-driven behavior change beyond what's documented in the `env` inventory row for this function.

## Capabilities found by reading, missed by the sweep

- **Raw WebSocket transport to the Codex backend** (openai-codex-responses.ts:1037-1650): the sweep's `network` class caught scattered `WebSocket`-string mentions but a reader has to follow `acquireWebSocket` → `connectWebSocket` → `processWebSocketStream` to see that this is a **second, independent network transport** (distinct from `fetch`) that: (a) caches live socket connections per `(sessionId, accountId)` for up to 55 minutes (`SESSION_WEBSOCKET_MAX_AGE_MS`) and reuses them across turns, (b) maintains cross-turn "continuation" state (`previous_response_id` + delta input) so a full conversation history is not always re-sent, and (c) on Bun, patches around a proxy-env bug by subclassing `WebSocket`. This is materially more attack surface than a stateless request/response API and was not obviously flagged by the regex sweep as a distinct capability.
- **zstd request-body compression via `node:zlib`'s builtin-module accessor** (openai-codex-responses.ts:211-238): `process.getBuiltinModule("node:zlib")` bypasses the module resolver entirely; the sweep's `dynamic-code` patterns (`vm`, `eval`, `import()`) don't match `getBuiltinModule`, so this call was invisible to the regex sweep even though it is a form of runtime module acquisition.
- **In-memory WebSocket session cache surviving across turns and models** (openai-codex-responses.ts:872-874, `websocketSessionCache`/`websocketDebugStats`/`websocketSseFallbackSessions` module-level `Map`s): state that outlives a single `stream()` call, cleaned up via `registerSessionResourceCleanup(closeOpenAICodexWebSocketSessions)` (line 927) when a session ends. Not a sweep pattern (no fs/network keyword on the cache itself) but relevant to reasoning about resource lifetime and cross-session leakage if `sessionId`s were ever reused across users/workspaces.
- **`/proc/self/environ` direct read as an env fallback** (utils/provider-env.ts:20-38): reads a `/proc` pseudo-file directly with `readFileSync` via `require("node:fs")` — not matched by the `env` sweep pattern (`process\.env\b` only) or by `fs-write` (it's a read). This is a legitimate, documented Bun-sandbox workaround, but it is filesystem access to a sensitive path that the regex sweep's `fs-write`-only filesystem class would never surface (it has no `fs-read` class).
- **`xai.ts`'s `validateVerificationUri` scheme allowlist** (line 51-62): a defensive control (reject non-`https:` verification URIs before they're ever opened in a browser) that the sweep does not and cannot detect as "a guard exists here" — it only flags raw capability keywords, not the presence/absence of validation. Worth highlighting positively: this is exactly the kind of hardening you'd want after an "open() a server-supplied URL" CVE class, and it is present.
- **PKCE as the actual mitigation for the loopback-server race** (auth/oauth/openai-codex.ts): the sweep has no "race condition" class at all; a human has to read `startLocalOAuthServer` + `createAuthorizationFlow`/`generatePKCE` together to see that binding port 1455 first only lets a local attacker observe the authorization `code`, not complete the exchange (the `code_verifier` never leaves process memory).

## Questions for the human reviewer

1. **`options?.headers` provenance** (openai-completions.ts:72-76, openai-responses.ts:43-47): `getClientApiKey` treats *any* pre-set `authorization`/`cf-aig-authorization` header as sufficient to skip the "no API key" error, returning the sentinel `"unused"`. This area does not decide where `headers` come from — `packages/coding-agent/src/core/model-config.ts`/`model-runtime.ts` do. Please confirm in that area's review whether a workspace-level (repo-committed) config file can set custom provider headers, because if so this is a path for a malicious repo to redirect authenticated traffic to a header-supplied credential instead of the user's configured key.
2. **`openai-responses-shared.ts:222` missing try/catch on `JSON.parse(block.thinkingSignature)`**: every *other* signature-parsing site in this scope (`openai-completions.ts:1213`, `openai-responses-shared.ts:60,525`) is wrapped in try/catch with a graceful fallback; this one is not. Is a crafted/corrupted `thinkingSignature` in an imported or cross-provider-replayed session (T1/T4-adjacent — session files are read from disk, potentially shared or synced) expected to hard-fail the turn, or should this be hardened to match its siblings? Recommend a small, low-risk fix if in scope for this pin.
3. **`PI_OAUTH_CALLBACK_HOST` env override** (auth/oauth/openai-codex.ts:44-46): defaults safely to `127.0.0.1`, but if set to `0.0.0.0`/a LAN address the OAuth callback HTTP server becomes reachable from the local network during the login window. Setting arbitrary env vars already implies meaningful host access, so this is likely accepted risk — flagging for the record since it's a variance from the hardcoded-loopback pattern used everywhere else in this file.
4. **Unsigned JWT decoding is used twice** (openai-codex-responses.ts:1579-1590 `extractAccountId`, auth/oauth/openai-codex.ts:103-113 `decodeJwt`) purely to read `chatgpt_account_id` out of the harness's own already-trusted access token — no verification is needed because the token's authenticity was already established by TLS + the OAuth exchange with `auth.openai.com`. Confirmed benign, but worth a one-line note in the review record so a future reader doesn't mistake "no JWT signature check" for a vulnerability in isolation.
5. **Scope boundary: Azure**: `openai-responses-shared.ts` (in this scope) is also imported by `providers/azure-openai-responses.ts` / `api/azure-openai-responses.ts` (out of this scope per the task's file list and per `CLAUDE.md`'s "Provider scope is OpenAI + xAI" rule, since Azure isn't one of the two runtime providers strape ships behind hunk 4's SDK trim). Any finding above that touches `openai-responses-shared.ts` therefore also affects the Azure code path; please make sure the area that *does* own `azure-openai-responses.ts` cross-references this file rather than re-auditing it from scratch.
6. **Credential persistence is out of scope here**: this area *acquires* OpenAI/xAI credentials (OAuth tokens, API keys) but never writes them to disk — that happens in `auth/credential-store.ts` (not in this file list). Please confirm the area covering `credential-store.ts` explicitly checks it against CVE-2026-54327 (auth.json write race), since the tokens produced by `openai-codex.ts`/`xai.ts` are exactly the secrets that CVE class is about.
7. **`onMessage` in `parseWebSocket`** (openai-codex-responses.ts:1287-1311) is a fire-and-forget `async` IIFE inside a synchronous event listener. If `decodeWebSocketData` or the queue/`wake()` logic ever threw *outside* the existing try/catch, the rejection would be unhandled.
